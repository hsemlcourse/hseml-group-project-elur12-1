## 1. Задача и метрика

По показаниям 13 IMU-сенсоров (ориентация + accel + gyro + mag) предсказываем 3D-позиции 14 суставов верхней части тела относительно Hips. Это многомерная регрессия: вход 305 чисел/кадр, выход 14×3 = 42 числа/кадр.

**Метрика — MPJPE** (Mean Per-Joint Position Error, средняя евклидова ошибка позиции сустава). Прямо интерпретируется в единицах длины (BVH ≈ см), не зависит от выбора осей. Доп. метрики: RMSE, MAE.

## 2. Данные

[TotalCapture](https://cvssp.org/data/totalcapture/) (CVSSP), subject S1: 12 записей × 4 категории движений (acting / freestyle / rom / walking), 60 Гц, всего **45 267 кадров**. Готовых парсеров нет — `.sensors`, `.bvh` и калибровки распарсены вручную ([src/preprocessing.py](../src/preprocessing.py)).

Грабли:
- Кватернионы в `.sensors` — порядок `wxyz`, в калибровках — `xyzw`.
- BVH-файлы Blender-экспорта: каждый сустав имеет 6 каналов (XYZpos + ZXYrot), но **position-каналы у не-root joints — статичные дубли OFFSET из HIERARCHY**. Реальное движение зашито в rotation-каналах → нужен полноценный forward kinematics (`R_world[j] = R_world[parent]·Rz·Rx·Ry`, `pos[j] = pos[parent] + R_world[parent]·OFFSET[j]`).
- IMU собираются из двух разных папок: `s1_Gyro_Mag/` (основной поток) + `s1_imu/` (калибровки).

Подробности — [data/DATA_INFO.md](../data/DATA_INFO.md).

## 3. Препроцессинг

**Feature engineering** (169 сырых → 305):
- Для каждого из 13 сенсоров: калиброванный кватернион в глобальной системе `R^g = R_ref⁻¹ · R_imu · R_bone` (4) + accel (3) + gyro (3) + mag (3) + конечные разности quat/accel/gyro (10) = 23 фичи.
- Плюс позиция Hips и её velocity (6).

**Таргет.** Глобальные позиции 14 суставов считаются через forward kinematics из rotation-каналов BVH, затем берётся **разница с Hips** (hip-relative) — убирает зависимость от глобального положения тела в пространстве (которое из IMU без интегрирования accel не восстанавливается).

**Сплит по записям**, не по кадрам:
- train: `acting1+2, freestyle1+2, rom1+2, walking1+2` (31 119 кадров)
- val: `acting3, walking3` (6 166)
- test: `freestyle3, rom3` (7 982)

Сплит по кадрам дал бы leakage (соседние кадры почти одинаковы при 60 Гц). Все 4 категории присутствуют и в train, и в hold-out.

**Стандартизация:** μ/σ считаются на train, применяются ко всем сплитам. Пропусков/дубликатов нет.

Визуализации EDA — [notebooks/01_eda.ipynb](../notebooks/01_eda.ipynb).

## 4. Baseline

`LinearRegression` на 305 стандартизованных фичах.

| Сплит | MPJPE | RMSE | MAE  |
|-------|------:|-----:|-----:|
| val   |  5.01 | 6.79 | 3.79 |

В единицах BVH (≈ см). 6.4 см на сустав — нормальный baseline для линейной модели на нелинейной задаче (композиция поворотов скелетной цепи).

## 6. Финальная модель и интерпретируемость

**Выбор: MLP (4 residual-блока × 512, dropout=0.15, 30 эпох, AdamW + cosine LR).** Лучший test MPJPE (1.83) среди всех испробованных. На обучение уходит ~70 секунд на Mac MPS, инференс — батч 512 за миллисекунды.

**Per-joint MPJPE** (test): концевые суставы (Hand, ForeArm) — самые сложные из-за накопления ошибок по кинематической цепи. Корневые (Spine, Spine1) — самые точные. См. [baseline_per_joint.png](images/baseline_per_joint.png).

**Per-action:** test `freestyle3` MPJPE заметно ниже, чем `rom3` (range-of-motion содержит экстремальные позы с большим вылетом конечностей — там модель ошибается сильнее).

**Интерпретируемость.**
- **Linear** (как baseline): веса агрегируются по сенсорам — для координат RightHand максимальный вклад дают R_LowArm и R_UpArm, что физически корректно (рука — ближайшие сегменты по кинематической цепи).
- **XGB/RF**: gain feature_importance подтверждает доминирование калиброванных кватернионов соответствующих конечностей.
- **MLP**: интерпретируется через градиентный saliency, выходит за обязательный объём проекта.

## 7a. Что изменилось после CP1: критический баг в препроцессинге BVH

При работе над деплоем (CP3) обнаружил, что в анимации скелета все 14 суставов
двигаются как один rigid body — артикуляции рук/корпуса нет. Диагностика показала
**фундаментальный баг в `parse_bvh`**, который аннулирует все результаты CP1.

**Симптом.** В предсказаниях `std` по времени для **всех** суставов равен `std` позиции
Hips и они движутся синхронно. То есть `Y[joint_t] = const - Hips[t]` для каждого
сустава — никакой артикуляции.

**Причина.** В CP1 я считал, что в Blender-BVH у каждого сустава первые 3 канала
(`Xposition Yposition Zposition`) — это глобальные координаты. **Это неверно.**
На самом деле для не-root joints эти каналы — статичные дубли `OFFSET` из секции
HIERARCHY (для Spine во всех кадрах ровно `(0, 1.81777, -2.72665)` = HIERARCHY
OFFSET). Реальное движение зашито в rotation-каналах (`Zrotation Xrotation
Yrotation`), которые мой парсер **полностью игнорировал**. Hips — единственный сустав,
position-каналы которого реально менялись от кадра к кадру.

**Последствие для CP1.** Таргет `Y = gt_pos[joint] - hips` в реальности равнялся
`T_pose_offset[joint] - hips[t]`. А `hips` явно присутствовал в фичах X (6 каналов
hips_pos + hips_velocity), поэтому линейная регрессия тривиально учила «инвертировать
hips» и получала MPJPE 0.11 — фиктивно низкая ошибка на бессмысленной задаче.
Все выводы CP1 о «линейности задачи» и «проигрыше нелинейных моделей» были
артефактом этого бага.

**Фикс.** Полноценный forward kinematics в `src/preprocessing.py`:

```
R_world[j]  = R_world[parent(j)] · Rz(z_j) · Rx(x_j) · Ry(y_j)
pos_world[j] = pos_world[parent(j)] + R_world[parent(j)] · OFFSET[j]
```

Что переписал:
1. Парсинг HIERARCHY со стеком открытых joint'ов → массив `parents[]` и `offsets[]`.
2. Из MOTION для каждого joint беру 3 rotation-канала; position-каналы у не-root
   игнорирую как избыточные. Для root беру position-каналы (глобальное движение Hips).
3. Векторизованная сборка матриц поворота `Rz · Rx · Ry` для всех 31k кадров через
   numpy, FK итеративно по joints (родители всегда раньше детей в BVH).
4. Защита от `End Site` блоков (у них нет CHANNELS, только OFFSET).

**Числа до и после фикса** (test MPJPE, см):

| Модель    | CP1 (баг) | После FK |
|-----------|----------:|---------:|
| Linear    |      0.11 |     6.40 |
| KNN       |     13.77 |     2.91 |
| RandomForest |   1.73 |     2.38 |
| XGBoost   |      1.40 |     2.04 |
| LightGBM  |      0.56 |     2.10 |
| **MLP**   |      5.04 | **1.83** |
| BiLSTM    |     14.51 |     3.62 |

Иерархия моделей перевернулась: теперь задача правильно ведёт себя как
нелинейная, **MLP — лучший** (а не Linear). Это согласуется с физикой:
кинематика скелетной цепи — это композиция вращений, нелинейная функция углов.

**Другие изменения после CP1:**
- Деплой целиком (CP3): FastAPI в Docker + matplotlib-визуализатор в локальном
  `.venv-viz` (см. §7).
- В GIF-анимации `deploy_anim.gif` теперь показаны **оба скелета** — pred (красный)
  и ground-truth из mocap (зелёный) — чтобы качество предсказания было видно
  визуально, а не только по числам.
- Отчёт сокращён и приведён к формату «гипотеза → проверка → результат» для
  экспериментов (раньше было полотно текста).

## 8. Выводы

- Реализован полный пайплайн: ручной парсинг 3 форматов TotalCapture (включая forward kinematics из BVH-rotations) → feature engineering с калибровкой кватернионов → сравнение 8 моделей → деплой через FastAPI/Docker с 3D-визуализацией.
- **Лучшая модель — MLP с MPJPE 1.83** на test. Бустинги (XGB 2.04, LGBM 2.10) и KNN (2.91) тоже бьют линейный baseline (6.40) — задача существенно нелинейна (композиция поворотов скелетной цепи).
- Ансамбли почти не улучшают лучшую одиночную модель — главные ошибки общие для всех моделей (концевые суставы, нетипичные позы в `rom3`).
- 14 pytest-тестов проходят; пайплайн воспроизводим (`seed=42`, фиксированный сплит по takes).

**Ограничения:** только subject S1 (нет кросс-субъектной оценки); бенчмарка против SOTA (DIP-IMU, TransPose) не делал; BiLSTM не сошёлся за 12 эпох на MPS.

**Что улучшить:** leave-one-subject-out CV, физические лоссы (bone-length consistency, smoothness), Transformer-encoder вместо BiLSTM, перенести MLP в production-образ.
