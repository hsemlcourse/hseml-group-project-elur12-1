## 1. Задача и метрика

По показаниям 13 IMU-сенсоров (ориентация + accel + gyro + mag) предсказываем 3D-позиции 14 суставов верхней части тела относительно Hips. Это многомерная регрессия: вход 305 чисел/кадр, выход 14×3 = 42 числа/кадр.

**Метрика — MPJPE** (Mean Per-Joint Position Error, средняя евклидова ошибка позиции сустава). Прямо интерпретируется в единицах длины (BVH ≈ см), не зависит от выбора осей. Доп. метрики: RMSE, MAE.

## 2. Данные

[TotalCapture](https://cvssp.org/data/totalcapture/) (CVSSP), subject S1: 12 записей × 4 категории движений (acting / freestyle / rom / walking), 60 Гц, всего **45 267 кадров**. Готовых парсеров нет — `.sensors`, `.bvh` и калибровки распарсены вручную ([src/preprocessing.py](../src/preprocessing.py)).

Грабли:
- Кватернионы в `.sensors` — порядок `wxyz`, в калибровках — `xyzw`.
- В этих BVH-файлах первые 3 канала сустава — это **глобальные координаты**, не оффсеты → forward kinematics не нужен.
- IMU собираются из двух разных папок: `s1_Gyro_Mag/` (основной поток) + `s1_imu/` (калибровки).

Подробности — [data/DATA_INFO.md](../data/DATA_INFO.md).

## 3. Препроцессинг

**Feature engineering** (169 сырых → 305):
- Для каждого из 13 сенсоров: калиброванный кватернион в глобальной системе `R^g = R_ref⁻¹ · R_imu · R_bone` (4) + accel (3) + gyro (3) + mag (3) + конечные разности quat/accel/gyro (10) = 23 фичи.
- Плюс позиция Hips и её velocity (6).

**Таргет.** Позиции 14 суставов **минус Hips** — убирает зависимость от глобального положения тела (которое из IMU без интегрирования accel не восстанавливается).

**Сплит по записям**, не по кадрам:
- train: `acting1+2, freestyle1+2, rom1+2, walking1+2` (31 119 кадров)
- val: `acting3, walking3` (6 166)
- test: `freestyle3, rom3` (7 982)

Сплит по кадрам дал бы leakage (соседние кадры почти одинаковы при 60 Гц). Все 4 категории присутствуют и в train, и в hold-out.

**Стандартизация:** μ/σ считаются на train, применяются ко всем сплитам. Пропусков/дубликатов нет. Выбросы не отфильтровываются (резкие пики gyro — полезный сигнал).

Визуализации EDA — [notebooks/01_eda.ipynb](../notebooks/01_eda.ipynb).

## 4. Baseline

`LinearRegression` на 305 стандартизованных фичах.

| Сплит | MPJPE | RMSE | MAE  |
|-------|------:|-----:|-----:|
| val   |  0.08 | 0.08 | 0.03 |
| test  |  0.11 | 0.11 | 0.04 |

Низкий MPJPE объясняется физикой: после калибровки в глобальную систему отображение «кватернионы → координаты суставов» близко к линейному, потому что длины костей константны.

| Модель                  | val  | **test** | время |

### Эксперименты в формате гипотеза → проверка → результат

| # | Гипотеза | Как проверял | Результат |
|--|--|--|--|
| 1 | Бустинги (XGB/LGBM) обыграют Linear за счёт нелинейности | Обучил оба на тех же фичах | **Нет.** Linear лучше (0.11 vs 0.6–1.4). Причина: `MultiOutputRegressor` тренирует 42 независимых регрессора — теряется shared structure между координатами. |
| 2 | KNN сработает, т.к. позы похожи на соседей в обучении | k ∈ {3,5,8,16,32}, weighted | **Нет.** test 13.8. В 305-мерии евклидова метрика плохо отражает физическую близость поз (curse of dim + неравные шкалы каналов). |
| 3 | MLP/BiLSTM выучат нелинейность | MLP 20 эпох, BiLSTM 12 эпох (MPS) | **Не сошлись до Linear.** MLP test 5.0, BiLSTM 14.5. Нужно сильно больше эпох + больше данных. |
| 4 | Ансамбль улучшит Linear | Усреднение Linear + {RF, XGB, LGBM} | **Ухудшает.** Linear настолько точнее, что усреднение разбавляет его сигнал. |
| 5 | Размерность сильно избыточна | PCA + Linear, varying k | 95% дисперсии — в ~50–80 компонентах. Linear+PCA(50) ≈ Linear без PCA → эффективная размерность ~6× меньше формальной. |
| 6 | Без quat качество резко упадёт (ablation) | Зануление по модальностям | Иерархия важности: **quat ≫ dquat > accel > mag ≈ gyro**. Без quat MPJPE растёт на порядок. |

Подробности гиперпараметров и PCA/UMAP — [notebooks/03_experiments.ipynb](../notebooks/03_experiments.ipynb).

## 6. Финальная модель и интерпретируемость

**Выбор: Linear Regression.** Критерии: лучший val (0.08), лучший test (0.11), мгновенное обучение, минимум памяти. Любая более сложная модель и любой ансамбль *хуже*.

**Per-joint MPJPE** (test):  концевые суставы (Hand, ForeArm) — ожидаемо самые сложные из-за накопления ошибок по кинематической цепи. Корневые (Spine, Spine1) — самые точные. См. [baseline_per_joint.png](images/baseline_per_joint.png).

**Per-action:** test `freestyle3` MPJPE = 0.07; `rom3` MPJPE = 0.13 (range-of-motion содержит экстремальные позы, хуже покрытые train).

**Интерпретация коэффициентов.** Веса Linear агрегируются по сенсорам — для координат RightHand максимальный вклад дают R_LowArm и R_UpArm, что физически корректно (рука — кинематически ближайшие сегменты).

## 7. Деплой

**Архитектура:** Docker-контейнер с FastAPI + sklearn (всё для инференса), отдельный локальный `.venv-viz` с matplotlib для визуализации (чтобы прод-образ не тащил heavyweight зависимости).

**Endpoints:**
- `POST /predict` — принимает JSON с массивом кадров (для каждого сенсора: `quat[wxyz]`, `accel`, `gyro`, `mag`) и калибровкой; возвращает `(T, 14, 3)` координат суставов + топологию (рёбра скелета).
- `GET /schema` — описание формата.
- `GET /health`, `GET /docs` (Swagger).

**Запуск:**
```bash
docker compose -f deploy/docker-compose.yml up --build -d        # API на :8000
python -m venv .venv-viz && source .venv-viz/bin/activate
pip install -r deploy/requirements-viz.txt
python -m src.client_example --start 100 --length 1   --out report/images/deploy_frame.png
python -m src.client_example --start 0   --length 240 --out report/images/deploy_anim.gif
```

**Демо-проверка end-to-end:**
- 1 кадр: API → MPJPE = 0.068, [deploy_frame.png](images/deploy_frame.png)
- 180 кадров: API → MPJPE = 0.053, [deploy_anim.gif](images/deploy_anim.gif)
- Healthcheck: `{"status":"ok","model_loaded":true,"n_features":305}`

## 8. Выводы

- Линейная модель с правильным препроцессингом (калибровка кватернионов в глобальную систему + velocity-фичи) даёт **MPJPE 0.11** — лучше всех испробованных нелинейных моделей и ансамблей.
- Главный урок: feature engineering на уровне физики задачи побеждает «бросить XGBoost и забыть». Сложные модели проигрывают, потому что (а) `MultiOutputRegressor` ломает связи между выходами, (б) NN-моделям нужно больше данных и эпох.
- Конец пайплайна: API в Docker + клиент с 3D-визуализацией matplotlib. Всё воспроизводится одной командой.

**Ограничения:** только subject S1 (нет кросс-субъектной оценки); бенчмарка против SOTA (DIP-IMU, TransPose) не делал.

**Что улучшить:** leave-one-subject-out CV, физические лоссы (bone-length, smoothness), Transformer вместо BiLSTM на больших окнах.
